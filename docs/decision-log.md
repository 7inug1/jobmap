# 잡맵 판단 기록

결정, 근거가 된 숫자나 사실, 버린 선택지를 함께 적는다. 날짜는 2026년 기준 월-일.

## 범위

- 11-07: 과제 3 마감(11-11 오전 6시)까지 범위를 "이력서와 공고 본문으로 근거 있는 비교"로 줄였다. 막혔을 때 Hermes로 옮기는 대신 범위를 줄이는 쪽을 택했다. 옮기면 남은 나흘 중 하루 이상을 다시 시작하는 데 쓴다.
- 11-07: GitHub 저장소 검사로 완료를 판정하는 기능은 처음 제출한 기획에 있었지만 뒤로 미뤘다. 체크와 실제 시간 입력으로 대신한다.
- 11-07: 공고 링크 읽기와 PDF 업로드는 11-12 이후. 글 붙여넣기부터 만든다. Flue 문서상 메시지에 PDF 첨부가 가능해 `pdfjs-dist` 없이 될 수도 있다.
- 11-09: 화면은 입력, 진행, 비교 결과까지 옮겼다. 확인 질문 화면과 오른쪽 에이전트 패널은 에이전트가 질문을 만들지 않는 지금 보여 줄 내용이 없어 뒤로 미뤘다. 주당 시간 입력도 쓰는 곳이 생길 때 넣는다.
- 11-09: 공고 링크 읽기를 11-12 이후에서 지금으로 앞당겼다. 사용자가 데모처럼 링크 입력이 있어야 한다고 판단했다. 서버는 공개 https 주소만 읽고, 불러온 글은 입력칸에서 고칠 수 있다. 글을 못 읽는 페이지는 붙여넣기로 대신한다.
- 11-09: 공고 플랫폼 15곳을 실제 링크로 쟀다. 9곳 읽음, 6곳 실패. 실패한 곳은 사이트별 코드를 만들지 않고 붙여넣기로 안내한다. 결과는 `docs/posting-sources.md`.
- 11-09: 지원 요건이 없거나 500자 미만인 글은 읽기 성공으로 치지 않는다. 잡코리아와 원티드에서 요약이나 주요 업무만 읽고 성공으로 처리된 사례가 있었다.
- 11-09: 이력서 PDF 첨부를 11-12 이후에서 지금으로 앞당겼다. 무료 모델이 PDF를 직접 읽지 못해 `pdfjs-dist`로 브라우저에서 글자를 꺼낸다. PDF에 적힌 순서를 유지해 2단 이력서가 섞이지 않게 했고, 추출한 글자는 화면에 보여 주지 않는다. 사용자는 PDF와 링크만 넣는다. Chrome으로 만든 PDF는 띄어쓰기가 제어 문자로 나와 근거 확인이 전부 실패했기 때문에 공백으로 바꾼다.
- 11-09: 입력 화면에 링크로 읽는 플랫폼과 붙여 넣어야 하는 플랫폼을 표시한다. 붙여 넣어야 하는 플랫폼은 불러오기를 막고, 처음 보는 사이트는 시도하게 둔다. LinkedIn은 읽히지만 자동 수집 약관을 확인하기 전까지 붙여넣기로 둔다.
- 11-09: 방향을 고르면 이번 주 할 일로 바로 이어지게 했다. 이력서 문장 화면은 AI 한도가 풀린 뒤 둘 사이에 넣는다. 할 일이 일주일 시간보다 커도 이번 주에 하나는 정한다.
- 11-09: 공고 읽기는 리다이렉트마다 주소를 검사하고 응답을 5MB까지만 읽는다. 비교 입력은 공고와 이력서 각 3만 자로 제한한다. 로그인과 호출 제한은 배포 전에 정한다.

## 프레임워크와 모델

- 11-07: `@earendil-works/pi-ai`를 1.4.0으로 고정했다. 최신 1.5.0에서 `Type` export가 빠져 Flue CLI 2.3.0이 실행되지 않았다.
- 11-07: 모델은 Workers AI `@cf/mistralai/mistral-small-3.1-24b-instruct`. 무료 플랜에서 4개를 시험했다. kimi-k2.6은 유료 전용(403), gpt-oss-120b와 llama-3.3-70b는 도구 결과를 받은 뒤 두 번째 호출에서 400 오류, mistral-small만 도구 호출과 한국어 답까지 성공했다. 실제 공고 비교 품질은 평가로 다시 확인한다.
- 11-07: 가짜 도구로 세 가지를 확인했다. 도구 결과가 `dynamic-tool` 파트의 `output`으로 온다. `useDataWriter` 진행 표시가 `data-progress` 파트로 실시간 갱신된다(같은 이름은 최신 값으로 바뀜). 같은 대화 ID로 새로 고침하면 기록이 복원된다.
- 11-09: Workers AI 도구 호출에서 일부 한글이 U+FFFD로 깨진다("웹", "쇼핑", "폼"). 무료 모델 중 대안이 없어 모델을 바꾸지 않고, 근거 문장은 원문에서 찾아 후보가 하나일 때만 복원한다. 모델이 쓴 자유 문장도 깨질 수 있어 화면은 도구 결과만 믿고 그린다. 가상 공고로 3회 실행해 3회 모두 저장 성공.
- 11-09: 모델이 도구 실패 뒤에도 "저장되었습니다"라고 답한 사례가 있었다. 저장 여부는 모델 문장이 아니라 도구 결과 상태로 판단한다.

## 작업 규칙

- 11-08: Vitest 설정을 `agent/vitest.config.ts`로 분리했다. Cloudflare Vite 플러그인을 함께 읽으면 `exports is not defined`로 테스트가 시작되지 않았다.
- 11-09: GitHub Actions 커밋은 `ci/github-actions` 브랜치에 보관한다. 올리려면 GitHub 로그인에 `workflow` 권한이 필요한데 과제 제출 조건이 아니어서 미뤘다. 그동안 타입, 테스트, 빌드, commitlint는 로컬에서 돌린다.
- 11-09: 화면의 상태 판단 함수는 Node 내장 테스트 러너로 검사한다. web에 테스트 패키지를 새로 설치하지 않아도 된다.

## 평가

- 11-09: 이력서와 정답은 `agent/eval/private/`에 두고 저장소에서 뺐다. 제출할 때 저장소를 공개해야 해서 개인 정보를 올리지 않는다.
- 11-09: Workers AI 호출마다 출력 한도 4096토큰을 넣는다. Flue가 한도를 보내지 않아 모델 기본값에서 도구 호출이 잘렸고, 실제 길이 공고 3개가 모두 저장에 실패했다. 수정 뒤 3개 모두 저장 성공.
- 11-09: 프롬프트에서 당근 공고 제목을 뺐다. 다른 회사 공고의 제목(자격 요건, 우대 사항 등)에서도 요건을 뽑아야 한다.
- 11-09: 이 모델의 한글 깨짐은 도구 호출 인자에서만 나온다. 강제 도구 호출 8회에서 인자의 약 6%가 U+FFFD였고, 일반 답변 8회는 0자였다. 스트리밍 여부와 무관했다. 그래서 새 문장을 쓰는 방향 제안은 도구 대신 일반 JSON 답변으로 받고 코드가 검증해 최대 3번 부른다.
- 11-09: 시험을 반복해 Workers AI 무료 일일 한도 10,000 뉴런을 소진했다(오류 4006). 방향 제안은 실제 모델로 끝까지 확인하지 못했다.

## 저장

- 11-07: 11-11까지는 대화 ID와 입력값을 브라우저에 저장한다. Flue 영구 상태를 화면에서 바로 읽는 API를 찾지 못했다. 여러 기기 동기화가 필요해지면 서버 DB를 정한다.

## 입력 검증과 실패 안내

- 11-10: `web/src`를 bulletproof-react의 `app`, `features` 구조를 줄인 형태로 나눴다. 파일이 폴더 없이 나열되고 `App.tsx`가 718줄이었다. 기능 폴더끼리는 서로 가져오지 않고, 같이 쓰는 타입과 호출은 `shared`에 둔다.
- 11-10: 모달은 공고를 링크로 읽을 수 없는 경우에만 쓴다. 사용자가 본문 붙여넣기와 다른 링크 중 하나를 골라야 흐름이 이어지기 때문이다. 나머지 입력 오류는 입력란 아래 문구로 둔다.
- 11-10: 입력 기준은 표준이 없어 정했다. 공고 최소 200자, 이력서 최소 50자(기존 값), PDF 10MB. 최대 3만 자는 서버 제한과 같다. 실제 사용을 보고 고친다.
- 11-10: 재시도는 비교와 방향 제안 모두 2번까지로 제한했다. 방향 제안은 실패 1회에 최대 900뉴런을 쓸 수 있고, 일일 한도를 다 쓰면 재시도해도 소용이 없어 버튼을 뺀다.
- 11-10: 프론트 검증은 안내와 뉴런 절약용이다. 길이 검사는 서버에도 두고, 호출 제한은 배포 전에 넣는다.
- 11-10: 화면을 에이전트와 같은 Worker에서 내보낸다. 주소가 하나라 `/agents`, `/api` 호출을 그대로 쓸 수 있다. 호출 제한을 넣기 전에 무료 플랜으로 먼저 배포했다. 무료 플랜은 한도를 넘어도 차단될 뿐 요금이 나가지 않는다.
- 11-10: 일일 한도가 UTC 자정 뒤 24분이 지나도 풀리지 않아, 안내 문구에서 오전 9시 약속을 뺐다.
- 11-10: Workers Paid로 결제했다. 무료 한도가 UTC 자정 뒤 1시간이 지나도 풀리지 않아 작업이 막혔다. 결제 2분 뒤 AI 호출이 다시 됐다.
- 11-10: 결제하면 넘친 호출이 요금이 되므로, 사람별 제한보다 서비스 전체 하루 총량을 먼저 넣었다. 비교 50회, 방향 제안 80회이고 한국 시간 자정에 초기화된다. 횟수는 Durable Object 하나에서 세서 동시 요청도 정확하다. 형식이 틀린 비교 요청도 Flue가 검사하기 전에 세므로 하나로 친다.
- 11-10: 일주일보다 큰 일은 코드로 주 단위 분량을 나눈다. 배포 환경 첫 실행에서 20시간짜리 일이 "이번 주 20시간"으로 나와 주 3시간 약속과 어긋났다. AI에게 잘게 나눠 달라고 하면 뉴런이 더 들어, 코드로 먼저 고치고 사용자가 이번 주에 뭘 할지 모르겠다고 하면 AI 방식을 더한다. 체크는 해낸 시간 기록으로 쌓고, 잘못 누르면 그 일의 마지막 기록만 지운다.
- 11-10: 데모의 상단 바(로고와 탭), 하단 영역, Noto Sans KR 글꼴을 옮겼다. 처음 화면을 옮길 때 바깥 틀을 빠뜨려 첫 화면으로 돌아갈 방법이 없었다. 탭은 이미 지나온 단계만 보여 주고, 로고는 이번 주 할 일(없으면 비교 결과)로 간다. 이력서, 지식 탭과 에이전트 패널은 기능이 생길 때 붙인다.
- 11-10: 휴대폰 폭(390px)에서 비교 결과가 3,143px로 길고 다음 버튼이 맨 아래에만 있었다. 요건 이름이 공고 줄과 같으면 다시 쓰지 않고, 버튼 줄을 화면 아래에 고정했다.
- 11-10: 첫 화면을 "넣을 것은 이력서와 공고 두 가지뿐"이 먼저 보이도록 번호 붙은 두 단계 카드로 바꿨다. 기준은 [디자인 원칙](design-principles.md)에 적었다. 사용자가 이력서와 공고 영역이 명확하지 않고 매력적이지 않다고 지적했다. 지원 사이트 목록은 접고, PDF는 끌어다 놓을 수 있게 했다.
- 11-10: 비교 진행 화면을 2단계에서 5~6단계로 늘렸다. 시간에 맞춰 넘기는 가짜 단계는 쓰지 않고, 이미 읽은 이력서와 공고의 글자 수, 저장 도구 호출에 담긴 요건 수, 근거 확인 중인 호출, 근거 불일치로 실패한 횟수처럼 실제로 받은 신호만 보여 준다.
- 11-10: 비교 결과를 스트리밍으로 보여 주도록 바꿨다. Flue는 도구 인자를 쓰는 도중의 내용을 화면에 보내지 않아, 저장 도구 대신 AI가 요건마다 JSON 한 줄을 글로 쓰게 했다. 화면은 끝난 줄을 바로 "확인 전" 판단으로 보여 주고, 응답이 끝나면 `/api/comparison/check`가 AI 없이 근거를 검사한다. 틀린 줄이 있으면 같은 대화에 고쳐 달라고 보내고 2번까지 다시 쓰게 한다. 저장 뒤 한 문장으로 답하던 호출이 사라져 비교 1회의 모델 호출이 2번에서 1번으로 줄었다.
- 11-10: 배포 환경 측정. 원티드 공고(요건 7개)에서 시작 버튼을 누른 뒤 첫 판단이 9.0초에 보였고 18.7초에 결과 화면으로 넘어갔다. 당근 공고(요건 15개)도 한 번에 검사를 통과했다. 같은 공고로 바꾸기 전과 비교한 수치는 아니다.
- 11-10: 정정. 일반 글로 받으면 한글이 깨지지 않는다고 봤는데(11-09 측정 8회 0자), 당근 공고 실행에서 글에도 `U+FFFD`가 나왔다. 서버 검사가 원문으로 되돌려 통과했다. 깨짐은 도구 인자에만 있는 문제가 아니므로 복원 단계는 계속 둔다.
- 11-10: 공고의 제목 구조를 화면이 추정하지 않고 원문 HTML에서 가져온다. 서버가 `<h1>`~`<h6>`은 단계만큼 `#`, 굵은 글씨만 있는 문단은 `##`, 목록은 `- `로 표시해 넘긴다. 당근 커뮤니티 공고에서 제목 14개("이런 분과 함께하고 싶어요", "이런 분이면 더 좋아요" 등)를 원문대로 읽었다. 제목 태그를 쓰지 않는 사이트(Lever)와 붙여 넣은 글은 이전처럼 모양으로 추정한다.
- 11-10: 진행 단계를 하나씩 차례로 체크한다(0.45초 간격). 이력서와 공고는 진행 화면이 뜨기 전에 이미 끝난 일이라 가짜 로딩에 가깝지만, 무엇을 거쳤는지 보이게 하려는 선택이다. 사용자가 "빠르다고 느낄 것 같다"고 판단했다. 입력 화면에서 한 번 보여 준 두 단계는 비교 화면에서 다시 체크하지 않는다.
- 11-10: 요건 이름이 `executionBalance`처럼 변수 이름이면 공고 문장으로 바꿔 보여 준다. 프롬프트에도 한국어 이름을 쓰라고 적었다. 영어로 쓴 공고의 요건 이름은 영어 그대로 둔다.
- 11-10: 공고 링크 읽기는 네트워크 오류, 429, 5xx일 때 서버가 한 번 더 시도한다. 사용자가 당근 공고에서 한 번 실패한 뒤 다시 시도하니 됐다고 했는데, 같은 링크 36번(공고 3개 x 12번)은 전부 성공해 원인은 확인하지 못했다. 일시적인 접속 실패로 보고 재시도를 넣었고, 재시도가 일어나면 로그에 남긴다.

- 11-10: 채울 방법은 한 번에 5개 요건만 받는다. 불충족을 먼저, 일부 충족을 그다음에 두고, 나머지는 방법을 고르는 화면 아래에 "아직 방법을 보지 않은 요건"으로 보여 준다. 버튼을 누르면 다음 5개의 방법을 이어서 받고 이미 고른 방법은 유지된다. 이유는 시간이 요건 수에 비례하고(13개 44~79초), 13개의 방법 30여 개를 한 번에 고르게 하면 "고민할 필요가 없다"는 약속에 어긋나기 때문이다. 배포 환경 측정: 요건 13개 중 5개 20.5초, 이어서 5개 19.7초. 사용자가 말한 최종 리포트 화면은 아직 없고, 나머지 요건 목록이 그 역할을 임시로 한다.
- 11-10: 사용자가 겪은 "근거 문장을 원문에서 확인하지 못했어요" 실패를 서버에 남은 대화 기록으로 분석했다. 네트워크 응답은 모두 200이었고, AI가 7번째 줄의 이력서 근거를 `Claude Code, Codex`로 적었는데 원문은 구두점이 다른 표기라 검사에서 걸렸다. 고쳐 달라고 두 번 요청했지만 AI가 같은 2,451자를 세 번 똑같이 돌려줘 실패로 끝났다. 고친 점: 글자와 숫자만 비교해 원문에서 한 곳에서만 맞고 6자 이상이면 구두점, 띄어쓰기, 대소문자만 다른 근거를 원문 문장으로 되돌린다. 글자가 다르거나 여러 곳에서 맞으면 되돌리지 않는다.
- 11-10: 한글이 `��`로 깨지는 원인을 재 봤다. 짧은 문장을 반복하게 한 Workers AI 호출 8회(일반 4회, 스트리밍 4회)에서는 깨짐이 0이었다. 실제 대화에서는 같은 줄이 세 번 똑같이 깨졌으므로, 전송이 아니라 긴 입력에서 모델이 일관되게 만드는 깨짐으로 본다. 근거 문장은 서버가 원문으로 되돌리고, 근거 확인 전의 비교 줄은 깨진 글자를 말줄임표로 가려 보여 준다.
- 11-10: 비교 중 "근거 확인 전" 줄은 계속 쌓지 않고 최근 4개만 보여 주고 접은 개수를 알려 준다. 요건이 15개면 줄이 15개 쌓여 화면이 길어지고, 아래 버튼이 밀린다. 다 비교하면 결과 화면에서 전체를 볼 수 있어 앞쪽 줄을 접어도 잃는 것이 없다. 직접 브라우저로 확인하지는 못했고 단위 테스트만 했다.
- 11-10: 채울 방법 제안이 가끔 실패하고 다시 누르면 되는 문제를 Cloudflare 로그로 봤다. 지난 1시간 `/api/directions`에 502가 2건(14:31, 15:06) 있었고 `directions_model_error` 로그는 없었다. 모델 호출이 오류를 던진 게 아니라 형식 검사를 세 번 모두 통과하지 못했다는 뜻이다. 어떤 검사에서 걸렸는지는 당시 기록이 없어 확인하지 못했다. 같은 요건으로 6번 다시 보냈을 때는 모두 성공해 재현하지 못했다.
- 11-10: 고칠 수 있는 항목은 거절하지 않고 고치도록 바꿨다. 없는 번호와 중복 번호는 버리고, 시간은 1에서 40 사이 정수로 맞추고, 깨진 글자가 있는 방법은 빼고 나머지를 쓴다. 빠진 요건, 방법이 없는 요건, 형식이 틀린 경우만 다시 쓰게 한다. 모델 호출이 일시적으로 오류를 던지면 남은 시도 안에서 다시 부른다(이전에는 바로 실패). 틀린 시도마다 `directions_attempt_failed` 로그에 문제를 남긴다. 같은 실패가 또 나면 이 로그로 원인을 볼 수 있다.
- 11-10: 화면마다 주소를 나눈다. React Router(`react-router` 8.5.1)를 설치했다. 입력 `/`, 비교 `/runs/:id`, 방법 고르기 `/runs/:id/directions`, 이번 주 할 일 `/runs/:id/plan`, 기록 `/history`. 사용자가 "리액트에서 엔드포인트 나누는 것처럼"을 요청했고, 표준 라이브러리를 쓰는 쪽이 직접 만든 라우터보다 뒤로 가기와 새로 고침 처리가 안정적이라 골랐다. 배포는 Workers 정적 자원의 SPA 설정(`not_found_handling`)이 이미 있어 주소를 직접 열어도 화면이 나오고, `/api`와 `/agents`는 계속 Worker로 간다(배포 환경에서 확인).
- 11-10: 로고는 `/`(처음 화면)으로 간다. 상단의 "공고 같이 보기" 탭은 쓸모가 없어 없애고, 오른쪽에 "내 기록" 링크를 두었다. 단계 이동은 각 화면 위의 "비교 결과, 방법 고르기, 이번 주 할 일" 표시로 대신하며 이미 갈 수 있는 단계만 눌린다. 아직 갈 수 없는 단계의 주소로 들어오면 갈 수 있는 단계로 돌려보낸다.
- 11-10: 비교 기록을 목록으로 쌓는다(`jobmap-runs`, 최대 20개). 비교를 끝낸 것만 `/history`에 보이고, 끝내지 못한 기록은 하루 뒤에 지운다. 로그인이 없어 기록은 만든 브라우저에만 있고 이력서가 들어 있어 화면에 안내를 넣었다. 탭을 여러 개 열어도 서로 덮어쓰지 않도록 저장할 때마다 저장소의 최신 목록에 합치고 다른 탭의 변경은 storage 이벤트로 받는다. 기록이 하나뿐이던 예전 저장 형식(`jobmap-run`)은 처음 열 때 목록으로 옮긴다.
- 11-10: 방법 고르기 화면을 고쳤다. 위쪽 담기 영역(지식에 남아요, 이력서에 남아요)은 헤더 아래에 고정했고 휴대폰에서는 두 칸으로 줄였다. 체크 표시는 18px에서 24px로 키우고 고른 항목은 채워서 보이게 했다. 이번 주 할 일의 체크박스도 22px로 맞췄다.
- 11-10: "나에게 해당하지 않는 요건이에요"를 카드 아래 텍스트 링크로 두었다. 장애인 및 보훈 대상자, 산업기능요원처럼 지원자의 신분에 따른 우대 조건이 불충족으로 나와 방법 카드까지 생겼기 때문이다. 별도 카드 버튼으로 만들면 방법 선택지와 같은 무게로 보여 링크로 했다. 뺀 요건은 방법 고르기와 이번 주 할 일에서 빠지고, 이미 고른 방법도 함께 빠지며, 화면 아래 목록에서 "다시 넣을게요"로 되돌릴 수 있다. 비교 결과의 충족 개수에는 아직 반영하지 않는다. 비교 단계에서 이런 조건을 아예 제외하는 방법은 AI가 우대 조건을 지나치게 빼는 위험이 있어 하지 않았다.
- 11-10: 방법 제안이 실패하던 원인을 찾았다. 형식 오류의 위치를 로그와 재시도 메시지에 적게 한 뒤, 개발 중 실제로 실패한 요청(요건 5개)을 다시 보내 확인했다. AI가 방법 중 일부에서 `recommended` 항목을 빼고 답하는데, 검사가 이 항목을 필수로 요구해 "답의 형식이 약속한 JSON과 다릅니다"로 거절하고 있었다. 세 번의 시도가 모두 같은 이유로 실패했고 4번 중 4번이 502였다(약 45초). 이전에 사용자가 겪은 "가끔 실패하고 다시 누르면 되는" 증상도 같은 원인일 가능성이 높다(당시 로그는 이유가 없어 확인하지 못함). `recommended`와 `description`을 선택 항목으로 바꾸자 같은 요청이 3번 모두 첫 시도에 통과했다(14~18초, 실패 로그 0건). 추천이 없으면 첫 방법이 추천된다. 형식 오류 안내에 틀린 위치를 적게 한 것은 재시도에서 AI가 고치는 데에도 도움이 됐다(고치기 전 같은 요청의 재시도가 성공함).
- 11-10: 데모의 이력서 기능을 살렸다. 방향을 고른 뒤 `/runs/:id/resume`에서 (1) 이력서 쪽이 확대되며 문장이 들어갈 자리를 보여 주고 (2) 문장을 하나씩 확인하며 할 일을 고치고 (3) 최종 이력서 미리보기에서 위치를 확인하고, 시작하면 이번 주 할 일로 간다. 이후 같은 주소가 이력서 문장 화면이 되어 할 일을 체크하고 실제 결과를 넣어 문장을 완성한다. 데모는 이력서를 미리 짜 둔 화면 조각으로 보여 줬지만 이 앱에는 PDF에서 읽은 글자뿐이라, AI가 문장과 함께 "기존 이력서의 어느 문장 아래에 넣을지"를 정하게 했다. 서버가 그 문장이 이력서에 실제로 있는지 검사하고(구두점만 다르면 원문으로 되돌림), 없으면 맨 아래 새 항목으로 모은다.
- 11-10: 이력서 문장에는 사실이 들어가므로 AI가 결과를 지어내지 못하게 했다. 아직 하지 않은 일의 결과는 `{빈칸}`으로 남기게 하고, 빈칸이 없으면 코드가 `{실제 결과}`를 붙인다. 할 일을 모두 체크해야 결과를 넣을 수 있다. 프롬프트의 예시를 따라 쓰거나 방법 설명에 없는 세부 내용(AGENTS.md, CI)을 끼워 넣는 경우가 있어(같은 입력 3번 중 1번) 확인 카드에서 사용자가 문장을 직접 고칠 수 있게 했다.
